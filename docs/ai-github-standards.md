# AI And GitHub Standards

These standards define how dotrepo coordinates Codex, Claude Code, Claude.ai,
ChatGPT, GitHub Copilot, and GitHub across related repositories.

## Standard Files Per Repo

Every managed project should converge toward this set:

```text
AGENTS.md
CLAUDE.md
.github/copilot-instructions.md
.github/PULL_REQUEST_TEMPLATE.md
.github/CODEOWNERS
.github/workflows/
docs/ai/context.md
docs/ai/sessions/
docs/ai/prompts/
docs/decisions/
```

## Instruction Surfaces

Use the smallest durable instruction surface that fits.

| Surface | Owner | Purpose |
| --- | --- | --- |
| `AGENTS.md` | Project repo | Codex startup rules, commands, standards, verification |
| `CLAUDE.md` | Project repo | Claude Code memory and startup rules |
| `.github/copilot-instructions.md` | Project repo | GitHub Copilot repo instructions |
| ChatGPT Project instructions | Web project | ChatGPT web behavior for the repo |
| Claude Project instructions | Web project | Claude.ai web behavior for the repo |
| `docs/ai/context.md` | Project repo | Safe short context pack for web tools |
| `docs/ai/sessions/*.md` | Project repo or local private notes | Handoff state between machines and tools |
| `docs/decisions/*.md` | Project repo | Durable architecture and workflow decisions |

Do not duplicate everything everywhere. Put stable, repo-specific engineering
rules in repo files. Put web-chat behavior instructions in web project
instructions. Put temporary state in session capsules.

## Web AI Best Practices

Use Claude.ai and ChatGPT web for:

- comparing designs
- reviewing documentation
- summarizing long context
- drafting standards
- creating test plans
- reasoning through math, APIs, or architecture
- preparing prompts for coding agents

Do not rely on web chat history as the source of truth. Promote useful results
into:

- project docs
- issue comments
- PR comments
- ADRs
- session capsules
- code patches

## Coding Agent Best Practices

Use Codex and Claude Code for:

- reading the working tree
- editing files
- running tests
- checking git state
- preparing commits
- applying standards generated by dotrepo

Before non-trivial changes, coding agents should read:

1. `AGENTS.md` or `CLAUDE.md`
2. `README.md`
3. `docs/ai/context.md`
4. latest relevant session capsule
5. project-specific architecture or standards docs

## GitHub Copilot Best Practices

Each managed repo should have `.github/copilot-instructions.md`.

It should include:

- project purpose
- package manager and Python environment expectations
- build and test commands
- lint/type-check commands
- important architecture boundaries
- files or directories Copilot should avoid changing casually
- security and privacy rules
- PR verification expectations

Keep this file concise. Copilot instructions should help Copilot produce and
review changes, not replace full documentation.

## GitHub Workflow Standards

Each managed repo should declare a workflow profile in `projects/inventory.yml`.

Common profiles:

- `library-python`: package build, tests, lint, dependency audit
- `jax-numeric`: CPU tests, optional GPU workflow, precision/parity gates
- `docs-heavy`: docs build, link check, generated-doc freshness
- `data-private`: strict private-data ignore rules and no public artifact upload

Each repo should have:

- a lightweight PR workflow where feasible
- manual full-test workflows for expensive checks
- dependency audit workflow when package dependencies exist
- docs validation workflow when docs are a published artifact
- optional self-hosted GPU workflow when CUDA is required

Use reusable workflows where they reduce duplication. GitHub documents reusable
workflows as workflow files in `.github/workflows` that are called with
`workflow_call`.

## PR Standard

Every PR should answer:

- What changed?
- Why?
- How was it tested?
- What are the risks?
- What follow-up remains?
- Did an AI tool materially contribute?

The PR template should make these fields automatic.

## Issue Standard

Every non-trivial issue should include:

- problem statement
- desired outcome
- affected repos
- acceptance criteria
- relevant docs or session capsules
- optional tools required
- whether dotrepo may update the repo automatically

## CODEOWNERS Standard

Use CODEOWNERS to request review for important areas:

- package metadata
- CI workflows
- docs standards
- AI instruction files
- release files
- private-data boundaries

Even for one-person repos, CODEOWNERS is useful documentation of ownership.

## Cross-Repo Change Standard

dotrepo scripts may update related repos only through this sequence:

1. Read `projects/inventory.yml`.
2. Run audit.
3. Generate a plan.
4. Apply managed templates or managed blocks.
5. Run verification.
6. Show git diff.
7. Commit if requested.
8. Push if requested.

Commit messages should use a consistent prefix, for example:

```text
chore(dotrepo): apply AI and GitHub standards
```

Pushes should default to the current branch unless a command explicitly creates
a new branch.
